# T3 Code 0.1.7: what the bridge relies on

The design study read upstream `main`. Jarvis runs the official stable 0.1.7, so every behavior the bridge needs was run again on 0.1.7.

- **Setup.** The official release was installed with `install.sh` into a throwaway `T3CODE_HOME` (`~/t3-acp-proof`) and served on port 47811.
- **Agents.** Two fake ACP agents were registered there as "Local ACP command" providers. One was a probe child that logs every frame and asks one question. The other was a scripted parent that turns messages into T3 MCP tool calls.
- **Line references.** These are to tag `v0.1.7` (commit `322f6544df`) of `pingdotgg/t3code`.

## Gaps

None of these blocks the design.

1. **The restart prompt is not a user message.** After `session/load`, T3 sends "Continue where you left off. …" as a prompt. The same text starts the usage-limit recovery prompt (`UsageLimitRecoveryWorker.ts:73`). The bridge treats a prompt with that prefix as "keep following the agent". It does not send it to Backstage.
2. **Replayed history would duplicate items.** T3 keeps the thread's history itself. So after `session/load` the bridge resumes the SSE stream after the last seq it showed, and it stores that seq per session on disk. A full replay would show every item twice.
3. **The MCP server arrives over stdio, not HTTP.** T3 gives a local ACP command its MCP tools as a stdio `t3 acp-mcp-bridge` process. Only flavors with `mcpOverHttp` get an HTTP entry (`adapter.ts:808-850`). The HTTP endpoint and its auth header are in that process's environment. The bridge does not use T3's MCP tools; the scripted parent uses the endpoint.
4. **Prompts carry T3's harness blocks.** A child's prompt wraps the brief in `<user_request>` and adds `<t3_code_instructions>`, `<runtime_info>` and `<pull_request_linking>`. The bridge sends only the `<user_request>` body to Backstage.
5. **Tool items show a summary, not each title.** The UI summarizes tool items by kind, for example "Ran 4 commands, changed 1 file, and performed 2 other actions". The stored item title is "Tool". The command and input stay on each item.
6. **Every cancel is a Stop.** Any `session/cancel` stops the cloud agent with `POST /agents/:id/stop`, because T3 sends it for Stop and for an interrupt alike. Shutting T3 down does not stop cloud agents. A restart resumes them.
